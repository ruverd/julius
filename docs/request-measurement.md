# Whole-request candidate measurement

`measure_request_pair(original, candidate)` serializes each complete xAI Responses request using the same `XAIAdapter.prepare` path used for sending. The byte counts therefore include instructions, tools, protocol fields, and all input items. `deltaBytes` is before minus after and may be negative. This offline comparison does not send either request.

Token counts stay `null` unless the caller injects a deterministic `token_counter(serialized_request_text)` with explicit `model_id` and `tokenizer_id`. The model ID must match the request's model field. Invalid counts fail closed. Any returned count is a caller-supplied diagnostic over the serialized JSON body. A caller may declare `token_counting_basis="model_input"`, but Julius cannot verify that the callback counted every model-visible field or provider framing. That declaration does **not** promote the count to measured direct model-input savings. `deltaTokens` stays signed and separate from provider-reported usage and billing.

`prepare_optimized_request` attaches this receipt as `PreparedXAIRequest.measurement`. Preparation still produces only a candidate with `sent: false`. `Julius.send_xai_optimized` returns a `requestMeasurement` receipt and records one request-scope transform tied to the first provider attempt. A complete response with matching response ID and actual model confirms that the request was accepted. The body's SHA-256 and byte length handed to the transport must also match the prepared candidate before Julius marks that transform sent. The hash alone does not prove delivery. Request-event token counts remain unavailable until a validated complete model-input counting contract exists. `tokenComparisonReason` explains the missing verification; Julius does not silently equate an alias with a different responding model.

xAI's [billing FAQ](https://docs.x.ai/developers/faq/billing) says inference endpoints add processing tokens, so even its [standalone tokenize-text endpoint](https://docs.x.ai/developers/rest-api-reference/inference/other) can differ from prompt tokens billed on an inference call. That endpoint accepts text and model, not a complete Responses request. Julius has no built-in verified xAI request-level token counter. The ordinary CLI safe path therefore reports serialized-byte change and provider-reported usage separately; direct input-token reduction remains unavailable.

The request-scope event describes the full serialized request; tool-output candidate events describe individual components. Do not add those two scopes as if they were independent savings. Neither byte change nor tokenizer count proves a cheaper task trajectory or financial savings.
