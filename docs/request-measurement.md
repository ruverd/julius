# Whole-request candidate measurement

`measure_request_pair(original, candidate)` serializes each complete xAI Responses request using the same `XAIAdapter.prepare` path used for sending. The byte counts therefore include instructions, tools, protocol fields, and all input items. `deltaBytes` is before minus after and may be negative. This offline comparison does not send either request.

Token counts stay `null` unless the caller injects a deterministic `token_counter(serialized_request_text)` with explicit `model_id` and `tokenizer_id`. The model ID must match the request's model field. Invalid counts fail closed. The default `tokenCountingBasis` is `serialized_request`: any returned count describes the JSON body only. It remains a diagnostic candidate comparison and **does not enter direct model-input savings**, even after an acknowledged send. The caller can explicitly attest `token_counting_basis="model_input"` only for a model-specific counter that interprets the complete request, including tool definitions and provider framing. Julius cannot verify that implementation; its identity and method must be independently audited. In either case, counts are `tokenizer_counted`, never provider-reported usage or billing. `deltaTokens` stays signed.

`prepare_optimized_request` attaches this receipt as `PreparedXAIRequest.measurement`. Preparation still produces only a candidate with `sent: false`. `Julius.send_xai_optimized` returns a `requestMeasurement` receipt and records one request-scope transform tied to the first provider attempt. It marks the transform sent only after a complete first response confirms the accepted request. Request-event token counts remain unavailable unless a model-input counter was explicitly attested and its pinned model exactly matches the responding model. `tokenComparisonReason` explains missing counters, JSON-only counts, unknown actual model, or alias mismatch. Julius does not silently equate a requested alias with a different response model.

xAI's [billing FAQ](https://docs.x.ai/developers/faq/billing) says inference endpoints add processing tokens, so even its standalone tokenize-text result can differ from prompt tokens billed on an inference call. Julius has no built-in verified xAI request-level token counter. The ordinary CLI safe path therefore reports serialized-byte change and provider-reported usage separately; direct input-token reduction remains unavailable.

The request-scope event describes the full serialized request; tool-output candidate events describe individual components. Do not add those two scopes as if they were independent savings. Neither byte change nor tokenizer count proves a cheaper task trajectory or financial savings.
