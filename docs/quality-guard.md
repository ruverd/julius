# Offline quality suspension guard

`julius.quality_guard.decide_suspension` makes a deterministic decision for one project, model, strategy, and strategy version. The caller supplies a versioned policy, task outcomes, and any explicit manual disable or re-enable actions. Julius does not fetch outcomes or call a model. The returned decision includes the policy version, record sequence IDs, sample count, known count and value for every metric, manual action, and suspension reasons so a caller can persist an audit trail.

After the minimum sample count, the guard checks error, recovery, and rework rates; mean latency; and total net USD savings against policy thresholds. A metric is unavailable if any task in the current window lacks that measurement. Missing values are never treated as zero. A known threshold breach suspends the scope even when another metric is unknown. Without a breach, unknowns yield `insufficient_evidence`. The opt-in SDK enforcement blocks optimization in that state.

Manual disable takes precedence. Manual re-enable begins a fresh evidence window after its sequence number, so old failures do not immediately suspend the scope again. Re-enable does not certify quality: the guard reports `insufficient_evidence` until enough new measured outcomes exist. The input records must have unique sequence numbers and task IDs within the scope. This module is an offline policy mechanism; fixture tests do not establish real task quality or causal savings.

`QualityStore(path)` persists scoped outcomes, manual actions, and each resulting decision in SQLite WAL. `append(record, policy)` commits the audit record and decision in one transaction; duplicate sequence numbers roll back. `decision(scope, policy)` recomputes under a write lock, so a changed policy cannot reuse stale clearance. `history(scope)` returns the stored audit inputs and latest decision. Record and decision storage failures propagate to callers.

The quality database is created with owner-only file permissions. Opening an existing database or SQLite sidecar with a direct symlink, unexpected file type, different owner, or group/other access fails rather than changing that file. Operators must repair unsafe permissions explicitly before using the guard.

`Julius.optimize(context, policy, quality_scope=scope, quality_policy=guard_policy)` opts into enforcement. The scope's project and model must match `context["projectId"]` and `context["modelId"]`; an unknown model cannot borrow another model's clearance. The scope must identify the implemented `repeated-lines` strategy at version `2`, preventing another strategy or the older line-only version from clearing it. Only `enabled` proceeds; manual disable, suspension, and insufficient evidence block before an artifact is created. Store access errors also block. The existing two-argument `optimize` call leaves the guard disabled for compatibility. Operators must ingest real task outcomes and manual actions into the same local quality store; this integration does not invent measurements or automatically re-enable a suspended scope.

The CLI exposes the same local store. `julius policy check --state-file guard.json` evaluates supplied outcomes without writing. `julius policy record --state-file record.json` appends one outcome or manual action; `julius policy status --state-file guard.json` recomputes the stored decision. The guard file contains `scope` and `policy`; a record file also contains `recordType` (`outcome` or `manual`) and `record`. `julius optimize tool-output.txt --project app --model model-id --profile safe --guard-file guard.json` enforces that decision before storing an original. These commands make no model call. Supplying a guard is explicit; Claude and xAI adapters do not yet gather task-quality outcomes automatically.
