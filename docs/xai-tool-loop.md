# xAI restore function-call loop

`run_restore_loop` explicitly sends an xAI Responses request through `XAIAdapter.send_once`. If the response asks for `julius_restore_artifact`, it reads the original from the project-scoped `ArtifactStore` and continues with a `function_call_output`, the same model, tools, authorization, and `previous_response_id`. A bounded `max_calls` limits restore work. Every attempted provider request yields an `XAIResult` in the returned `attempts` tuple for later usage recording.

The loop stops on any other function call, malformed arguments, repeated call ID, missing response ID, unavailable original, incomplete response, transport error, or call-limit excess. It never retries an ambiguous send. It does not execute arbitrary tools. A caller must explicitly authorize the initial request, including any xAI server-side tools in it.

The initial request must declare the Julius restore function and must not set `store: false`. The loop uses `previous_response_id` for continuation, while xAI documents `store: false` as disabling later response retrieval; compatibility between those features is not verified. Julius rejects that combination before sending instead of silently changing the caller's storage choice. This is a conservative inference from the [Responses API reference](https://docs.x.ai/developers/rest-api-reference/inference/responses), not a provider guarantee about every account.

This is fixture-tested plumbing, not a live compatibility claim. The caller must record all attempted usage, including an incomplete attempt, and must not turn estimates into realized savings. The loop does not itself write ledger events.

`Julius.send_xai_with_restores(...)` is the explicit SDK entry point. It records each attempted call before a continuation can be sent, including incomplete continuations. Events have distinct request and attempt IDs. The first call is categorized as `primary`; later calls that return restored material are `restoration`, and all costs remain in the task total once. Provider-reported model, token counts, and charge provenance are retained when available. It returns the per-attempt receipts and final loop status; it does not optimize the input or claim direct savings. The caller must arrange safe optimization separately and authorize dispatch.

The continuation fields follow [xAI's official function-calling example](https://docs.x.ai/developers/tools/function-calling): a `function_call` output item carries `name`, `arguments`, and `call_id`; the next request carries a `function_call_output` with `call_id` and `output`, plus `previous_response_id`.

`Julius.send_xai_optimized(...)` adds an explicit safe preparation step for eligible `function_call_output` text. It stores and verifies originals, sends the prepared copy through the restore loop, and records one `tool_output` transform event per candidate with heuristic evidence. A transform is marked `sent` only after a complete first provider response confirms acceptance; an ambiguous failure leaves it unsent. The event carries no tokenizer, so its estimated token difference does not become measured direct request-token savings. Every provider attempt, including restoration continuations, is recorded independently. `store=false` and unsupported input shapes fail before dispatch.
