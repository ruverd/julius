# Paired benchmark registration

`julius.evaluation_protocol.BenchmarkProtocol` registers a versioned, offline benchmark before any outcome is observed. Every task binds a stable task ID to a SHA-256 hash of its frozen snapshot through `FrozenFixture`. Each arm records its exact client, model, runtime, implementation versions, configuration, and cache state. Each task must be eligible for the native baseline and at least one candidate (Headroom, RTK, Context Mode, or a compatible combination). Distinct arm IDs may register multiple configurations of the same optimizer. A combination arm explicitly lists two or three distinct optimizer components; individual arms have no component list. Only eligible baseline/candidate pairs are assigned. Each candidate has its own predeclared English and Portuguese stratum counts, which must exactly match its eligible frozen tasks; this preserves the denominator for modality-specific arms. A confirmatory registration requires a written sample-size rationale or power assumption; the module does not calculate power. A pilot registration is exploratory and cannot be presented as confirmatory evidence.

The predeclared criterion records the success grading rule, success-rate noninferiority margin, efficiency measure, and minimum relative reduction. `assignment_plan` orders every baseline/candidate pair with a seeded random generator, includes all frozen tasks, and returns SHA-256 hashes of the canonical manifest and assignments. The receipt contains no observed quality result or efficacy claim. Save the complete manifest and receipt before execution; later analysis must verify their hashes and complete attempts against the same task and arm IDs. This module performs no task execution, model call, grading, or statistical inference.

Versions, cache details, and configuration are caller-supplied declarations. Their presence does not establish live client compatibility or that a run actually followed the registered environment. A credible quality claim also needs independent task selection, blinded grading where practical, complete attempt records, and analysis under the predeclared rule.

Before analyzing results, call `audit_execution_adherence(protocol, observations)` with one `ObservedExecution` per actual task, pair, arm, and attempt. Each record carries the frozen snapshot hash, manifest and assignment hashes, seed, planned order position, an observed `execution_sequence`, arm identity, versions, configuration, and cache state. Record `execution_sequence` at execution time as a strictly increasing integer across the run; it must be unique, and all attempts in the first arm must precede all attempts in the second arm for each pair. The audit checks this chronology and the registered metadata, detects missing and excess observations and repeated or skipped attempt indices, and compares **fully valid** pair counts with each candidate's planned locale/stratum denominator. A pair with any metadata, hash, or chronology issue is excluded from the observed denominator. A native baseline run shared between candidates must appear in each candidate's pair records. The result has `valid: false` and explicit issue codes when evidence is missing, unknown, or inconsistent. Its quality, economy, and efficacy fields remain null even when adherence passes; scoring and statistical analysis are separate steps. Metadata is supplied by the caller, so a passing audit verifies consistency of the supplied records, not independent authenticity or live compatibility.
